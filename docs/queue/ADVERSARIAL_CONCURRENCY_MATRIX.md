# Adversarial queue concurrency matrix

Status: bounded engineering contract for WU-L5-QUEUE-CONCURRENCY (#578).
Contract version: `queue-concurrency/v1`.

This matrix translates the deterministic queue invariants from Epic #5 and `queue-ordering/v1` into race-oriented acceptance cases. Implementations must serialize committed queue mutations so that identical committed history yields identical service order and ETA inputs. Retries must be idempotent and exceptional overrides auditable.

For every row, the target session and target QueueEntry IDs are fixed before the barrier is released. Tests must not choose a winner from wall-clock request arrival, worker scheduling, or process-local collection order.

| Race | Required invariant / serialization point | Deterministic expected outcome | Test oracle |
| --- | --- | --- | --- |
| Two check-ins for the same appointment-backed entry | One canonical active queue entry per appointment/patient/session identity; serialize under the existing session/entry queue-mutation lock order | Exactly one state transition assigns the entry's `eligibility_order`; an exact retry reuses the committed result and a conflicting operation identity is rejected | One active entry, one immutable registration identity, one committed eligibility slot, no duplicated ETA contribution |
| Two independent check-ins for different entries in the same session | The session mutation lock serializes eligibility assignment; service order uses committed `eligibility_order`, then immutable `registration_order` | Both may commit. The first serialized check-in receives the lower `eligibility_order`; the second receives the next value. Request arrival timestamps and worker scheduling are irrelevant | Ascending `eligibility_order` exactly reconstructs the committed check-in order; `registration_order` is only the deterministic fallback required by `queue-ordering/v1` |
| Two `call-next` attempts for one session | Session serialization plus the one-`called`-entry invariant; each command targets a concrete candidate entry after canonical selection | The transaction serialized first may transition only the canonical first eligible entry to `called`. A concurrent loser must re-read; while a `called` entry still occupies the session call slot it is rejected rather than claiming another entry. A later new command may select again only after the state machine permits it | No entry is called twice; at most one `called` entry exists per session; selection matches `queue-ordering/v1` |
| `call-next` races with check-in | Both operations serialize on the same session mutation boundary and eligibility is evaluated from committed state | Call-first: the later check-in is not retroactively eligible. Check-in-first: the newly committed `eligibility_order` participates in canonical selection | Outcome matches lock/commit serialization, never wall-clock handler timing |
| Priority override on entry A races with `call-next` for the same session | Override is authorized for a concrete clinic/session/entry, records actor+reason, locks through the queue mutation order, and rewrites only `priority_order`; call selection serializes on the same session boundary | Override-first: entry A's new committed priority participates in selection. Call-first: the already committed called entry remains called and the override may affect only a still-eligible target for a later selection | Audit names target entry A, actor, reason and resulting order version; selected entry is explainable from the immediately preceding committed version |
| Two priority overrides targeting the same entry A | Both commands require authorized actor, reason, stable idempotency identity and the same session serialization boundary | First valid commit produces one audited priority state/version; second re-evaluates the newly committed state and either commits the next valid priority version or is rejected by its stale/conflicting precondition. No worker-local "last writer" rule exists | Complete ordered audit history; effective `priority_order` derives from committed version order only |
| Two priority overrides targeting different entries A/B in the same session | Session-level serialization protects the ordered priority cohort; each command has an explicit target and audit identity | Each valid override is applied in serialization order and any cohort renumbering is committed atomically. The final cohort is reconstructable from the two committed audit events | No duplicate priority slot, no lost audit event, deterministic final cohort |
| Cancellation of entry A races with `call-next` | Both commands target/lock the same session and A when applicable; terminal/ineligible state cannot be overwritten | Cancellation-first excludes A from selection. Call-first may transition A to `called`; a later cancellation is then accepted or rejected only according to the canonical `called -> cancelled` rule and its explicit cancellation source/reason | No history rewrite; final state follows the legal transition graph and audit order |
| No-show of entry A races with `call-next` | `no_show` is legal only from the canonical states and requires its audited reason; call selection uses the same session serialization | No-show-first removes A from eligibility. Call-first may place A in `called`; a later no-show may then apply through the canonical `called -> no_show` transition, never by pretending A was never called | Audit order and state sequence are legal and replayable; no backward transition |
| Session close/pause races with `call-next` | Session lifecycle transition and queue call share the documented session lock/state gate | Close/pause-first blocks a new call. Call-first preserves the already committed `called` transition; subsequent lifecycle behavior follows the existing close/pause contract | No call is created from a snapshot serialized after the session became ineligible for calling |
| Session closure races with check-in | Closed sessions cannot accept newly eligible queue work | Closure-first rejects the check-in under canonical session-state validation. Check-in-first remains a historical committed entry and is handled by the existing closure semantics | No hidden deletion or process-local reordering of the committed entry |
| Cancellation of entry A races with a priority override targeting A | Same concrete entry/session target, authorization and queue lock order; terminal state dominates ordering metadata | Cancellation-first makes the later override invalid. Override-first is audited, then cancellation removes eligibility and clears/normalizes priority according to existing queue semantics | Cancelled A never returns to eligible order because of a stale override |
| Retry after ambiguous timeout of check-in | Actor-scoped idempotency receipt identifies the exact command payload | Exact retry returns the original committed result if the first commit happened, otherwise the operation commits once; changed payload under the same key is rejected | At most one transition/eligibility assignment and one logical audit side effect |
| Retry after ambiguous timeout of `call-next` | Command identity is bound to one concrete entry/payload and cannot advance service twice | Exact retry returns the originally committed called result; it cannot call a second patient | One command identity maps to one queue-entry result |
| Retry after priority/cancel/no-show mutation | Mutation identity and current canonical state prevent duplicate or stale transition | Exact replay is stable; changed payload or stale incompatible state is rejected/reconciled against current committed state | No duplicate audit side effect; stale operation cannot overwrite newer state |
| Simultaneous mutation of one entry from two workers | Session/entry lock order exposes one serialization winner and forces loser reconciliation | One legal transition commits; loser re-reads and either applies a still-legal subsequent transition or returns conflict | No last-write-wins overwrite based on stale state |
| ETA recomputation races with any queue mutation | Published ETA revision is bound to the committed queue/session version used as input | A candidate computed from an older revision cannot overwrite a newer estimate; mutation creates/marks the newer source revision | ETA payload/revision identifies its committed source version and stale publication fails closed |

## Cross-cutting acceptance rules

1. Tests must control serialization order with barriers or explicit transaction locks rather than sleeps or scheduler luck.
2. Every mutating command must identify its clinic, session, concrete target entry when applicable, actor, operation/idempotency identity, and required reason/source metadata before the race begins.
3. Authorization is evaluated before mutation and again wherever the existing command path reauthorizes a durable receipt; a test may not treat provider/worker identity as authorization.
4. A conflict is not success: the losing worker must re-read committed state before deciding whether another action remains valid.
5. Registration/service ordering uses `queue-ordering/v1`: `priority_order`, then committed `eligibility_order`, then immutable `registration_order`. Request arrival timestamps are never an ordering source.
6. Cancellation, no-show, closure and consultation activation are state-machine transitions, not destructive deletion of history.
7. ETA publication must include the queue/session source version so stale computations can be rejected.
8. Adversarial tests should execute both serialization orders for every two-way race above and repeat retry cases after simulated drop-after-commit responses.

## Implementation follow-up hooks

- Add PostgreSQL transaction/integration tests that force each serialization order with barriers or explicit transaction locks.
- Add command-level idempotency tests for check-in, call-next, priority, cancellation and no-show.
- Add state-machine property tests asserting one-called-per-session, one-active-consultation-per-doctor, and no duplicate active queue entry invariants.
- Add ETA stale-write rejection tests keyed by committed queue/session version.

This document defines testable concurrency behavior only. It does not authorize deployment, production mutation, or changes to the product ordering policy.
